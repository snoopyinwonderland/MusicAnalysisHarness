## 개발 목표와 설계 기준

악보의 시간 구간별 화음·전위·성부 진행·비화성음·조성·종지 및 불확실성을 설명하고, 이후 구조 분석과 작곡·편곡이 이 결과를 이용하게 한다. 음악적 역할·반주 질감·모티프 전개·앞뒤 배치를 별도 의미 데이터로 보존하며, 최소 지향 범위인 전곡 피아노 솔로와 듀엣·트리오·쿼텟의 생성으로 연결한다. 관현악과 장형식 스타일 작곡은 상위 목표이며 현재 구현 완료가 아니다.

- Canonical Core에는 관찰 가능한 음악적 사실만 둔다. 화성 해석은 별도 분석 계층이다.
- 원주석, AI/규칙 후보, 사용자 교정, 검수 승인, 학습 자격을 분리한다.
- 모든 주장은 원음표 ID, 유리수 시간 범위 `[start,end)`, 원본 및 분석 버전에 연결한다.
- 특정 작품/마디의 정답을 하드코딩하지 않는다. 사용자 사례는 일반 규칙의 근거와 반례로 기록한다.
- 교재 독해, 규칙 구현, 실험 통과, 음악적 정확도, 운영 적용을 각각 구별한다.
- 분산화음과 장식음은 앞뒤 실제 음표·지속·성부 진행으로 대조한다. 음을 삭제하거나 후보 수를 정확도로 해석하지 않는다.

공통 계약은 [Canonical IR 규격](../../MUSICANOTE_Canonical_Music_IR/CANONICAL_MUSIC_IR_SPEC_v0.1.md), 장기 개발 범위는 [통합 실행 계획](../../MUSICANOTE_Canonical_Music_IR/HARMONY_COMPOSITION_HARNESS_IMPLEMENTATION_PLAN.md)을 따른다. 구조 분석의 별도 기록은 유지하며 양쪽을 변경할 때만 상호 연결한다.

## 앞으로의 기록 규칙

구현 변경 때마다 개발 로그를 갱신한다. 현재 상태가 바뀌면 이 문서의 표도 갱신한다. 상위 계획·문서 지도에는 상세 실험 결과를 중복 누적하지 않고 개발 문서로 연결한다. 인수인계 문서는 실제 전달 요청 때만 요약한다.

각 개발 항목의 최소 내용:

1. 날짜/기록 ID, 문제·목표, 사용자 원문과 개발자 해석의 구분.
2. 음악 이론 근거, 관측 사실, 경쟁 가설, 일반 규칙과 보류 조건.
3. 변경 파일/함수/버전 또는 코드 hash, 적용 범위.
4. 사례 ID·원자료 경로/hash·IR ID·음표 refs·시간 구간·앞뒤 문맥.
5. 입력 선정 기준/split, 실행 명령·환경, 변경 전후 결과·반례·실패·누락.
6. 코드 작성/테스트/offline/화면/운영 상태를 분리해 표시.
7. 채택·실험 유지·보류·기각 결정과 이유, 다음 과제.

잘못된 기록은 정정 이유와 후속 버전을 남긴다. 과거 실패나 사용자 의견을 삭제하지 않는다. 기록이 있다는 사실과 자동 DB 강제·전체 누락 감사가 완료됐다는 사실을 혼동하지 않는다.

## 자료 및 공개 범위

원책·코퍼스·재현용 악보/IR·실험 출력은 로컬 자료 보관 정책을 따른다. 문서 정리는 원자료 업로드나 공개 허가가 아니다. 공개 제외 대상인 기존 교재 상세 문서는 이 폴더로 복제하지 않으며, 기존 공개 제외 결정을 유지한다. GitHub 업로드는 이번 문서 정리에 포함되지 않는다.
