# 화성 규칙 개발 검토와 공동 선택·학습·평가 우선순위

기록 ID: `HARM-REVIEW-20261004-46`

상태: **코드·개발 기록·공식 연구 자료에 근거한 검토 및 개발 계획 변경**. 선택기 구현, 가중치 학습, 공개 모델 실행 또는 새 정확도 측정을 완료한 기록이 아니다.

## 1. 결론과 채택 범위

사용자 검토 의견의 핵심인 **실제 화음 선택과 객관적인 평가를 이제 우선해야 한다**는 지적을 채택한다. 근거 규칙을 더 세밀하게 만드는 것만으로 분석 성능을 입증할 수 없다. 이후에는 첫 end-to-end 선택·평가를 가로막는 치명적인 입력 문제만 선행 교정하고, 지연 해결 등의 세부 보완은 평가에서 확인되는 주요 오류에 따라 진행한다.

기존 Canonical Core, 출처, 정확한 시간·음가, 후보와 경쟁 해석, 사용자 사례, 교재 규칙 및 회귀 검사는 유지한다. 이들이 최종 선택을 영구 보류하는 이유가 아니라 **선택의 특징량과 설명·진단 근거**로 작동하게 만든다. 자동으로 고른 결과는 검수된 정답과 별도 저장한다.

| 검토 의견 | 판단 | 반영 또는 정정 |
|---|---|---|
| 교재 수준 규칙에 비해 최종 화음과 정확도가 없다 | 새 공동추론 엔진에 대해서는 타당 | 실제 진행 선택과 주석 기반 독립 평가를 다음 최우선 기능으로 변경. 규칙의 교재 수준 완성도 자체는 검증된 것으로 단정하지 않음 |
| 경계를 먼저 정하는 것이 문제이며 공동 추론으로 풀린다 | 방법은 타당, 원인·해결 단정은 과도 | 경계×화음 공동 후보는 이미 구현됨. 부족한 것은 학습 가능한 점수·실제 선택·평가이며, 공동 추론도 조성/NCT/후보 누락 문제를 자동 해결하지 않음 |
| 규칙 가중치를 DCML에서 학습한다 | 채택 | 관측·해결·경계·전이 특징을 train 분리에서 학습. 음악적 전형은 soft evidence로, 참조 무결성은 hard constraint로 구분 |
| 고전 주석은 충분하고 팝 Melody 화음 파트가 중요하다 | 첫 실증에는 동의, 범용 충분성·자료 우열은 미확정 | 고전 첫 학습·평가를 더 미루지 않음. 팝 화음 파트는 중요한 weak/silver 자료이나 기능화성 gold로 자동 승격하지 않음 |
| ChordGNN·AnalysisGNN과 같은 평가표가 실질적 척도다 | 채택, 비교 조건 필요 | 같은 악보·분할·라벨·시간 좌표·지표로 비교. 공개 사전학습 자료와 테스트 중복을 표시하고 논문 숫자와 로컬 숫자를 직접 순위 비교하지 않음 |

이 기록이 단계45의 “다음: 지연/재등장 해결 전략부터”보다 **현재 실행 우선순위에서 우선**한다. 단계45 결과나 과거 검증 기록을 소급 변경하지 않는다. 지연/재등장·페달·조성·종지 작업은 취소가 아니라 후속 오류 개선 목록으로 이동한다.

## 2. 현재 구현에 대한 실제 확인

### 2.1 이미 있는 것과 없는 것

- [진행 탐색 코드](../../../src/musicanote_harness/harmony_progression_search.py)의 `search()`는 같은 문맥에서 서로 다른 구간 분할과 화음 reading을 함께 제안한다. DP 상태는 끝 시간점과 segment 수이며, 각 edge는 span과 화음 후보를 함께 가진다.
- 기본 제한은 `max_segments=6`, `per_state_limit=6`, `max_complete_paths=24`다. 보존된 후보를 실제 정답의 전체 집합으로 볼 수 없다. 이 제한으로 올바른 진행이 빠지는지 먼저 측정해야 한다.
- 현재 특징은 원시 비구성음 음표-시간, 철자 미지원, 보류 노출 및 낙관적인 국소 NCT 가능량이다. 마지막 값은 한 성부 가정에서 검증된 NCT 설명이 아니라 제안 탐색용 상계다.
- [공동 비교 코드](../../../src/musicanote_harness/harmony_progression_joint_comparison.py)는 하나의 성부 가정 안에서 완전 진행을 비교하지만 `selected`와 `preferred`는 `null`, `ranking_performed`와 `accuracy_measured`는 `false`다.
- [2026-10-01 공동 탐색 기록](2026-10-01-progression-search-and-joint-comparison.md)도 이 구별을 명시한다. 따라서 “새 엔진이 경계를 먼저 확정한 뒤 이름만 붙인다”는 설명은 현재 코드 전체를 정확히 나타내지 않는다.
- [단계45](2026-10-04-triad-seventh-obligation-policy.md)는 소나타 한 문맥의 각2,315후보·1,395쌍을 검사했으나 최종 선택과 음악 정확도는 측정하지 않았다. 후보·쌍·unit test 수는 작품 수나 정답률이 아니다.

이전 표면·펼친 화음 분석과 화면용 엔진에는 선택 결과가 있다. [분산형 통제 benchmark](../../../src/musicanote_harness/harmony_arpeggio_benchmark.py)는 선택 결과를 인공적으로 만든 의도와 비교한다. 따라서 “프로젝트 전체에서 한 번도 화음을 고른 적 없다”는 표현은 부정확하다. 그러나 **현재 개발 중인 새 엔진의 독립 전곡 정확도를 모른다**는 비판은 유효하다. 기존 화면 결과와 새 연구 엔진 결과를 섞어 진척을 주장하지 않는다.

### 2.2 데이터 상태를 정확도로 바꾸지 않기

[2026-09-24 DCML 저장 정렬 보고서](../../../output/dcml-batch-repeat-v2-2026-09-24/batch_summary.json)의 수치는 candidate1,129쌍, complete candidate392쌍, 준비392개, alignment eligible333개다. **당시 정렬 snapshot의 숫자**이며 오늘 전체17개 폴더를 재정렬한 수, 중복 제거된 독립 작품 수, 학습 허가 또는 음악 정답률이 아니다.

오늘 DCML 아래17개 하위 폴더의 존재를 확인했다. [이전 검토 cohort](../../../output/harmony-review-cohort-2026-09-26/report.json)에는 reserved/holdout과 `automatic_training=false` 등 자격 필드가 있다. 새 학습 manifest는 기존 제한을 자동 해제하지 않고 출처·사용 조건·실제 노출 이력을 다시 확인한다. reserved 내용은 이번 검토에서 열지 않았다.

`MusicXML/10,000 Reasons Melody.musicxml.xml`을 원본 XML로 확인하면72마디, P1에는 `<chord>` member0개, P2에는272개이고 양쪽 `<harmony>` 태그는0개다. 즉 Melody라는 파일명에서도 **기보된 화음의 음표들**과 **기능화성 주석**은 별개다. 이 표본 하나로 모든 Melody 자료의 품질을 일반화하지 않는다.

## 3. 공동 선택기의 계약

### 3.1 선택 대상

한 진행 가설은 다음을 함께 갖는다.

- 연속 범위 `[start,end)`를 덮는 경계와 화음 목록.
- 근음 철자, 화음 성질, 전위, 국소 조성 및 적용 대상의 후보. 미지원 어휘는 명시적으로 남긴다.
- 동일 진행 전체에서 일관된 성부 연결/NCT/생략·페달 가정과 원음표 근거.
- 점수, 경쟁 대안, 선택/보류 상태 및 모델·규칙·입력 버전.

화음 이름이 같은데 전위가 달라진 구간, 같은 음집합인데 조성/기능이 달라진 구간, DCML의 페달·계류 표기를 단순 화음으로 환원한 구간을 구분한다. `selected_prediction`은 모델의 최선 추정이며 `validated_annotation`이 아니다. 구체적인 필드와 schema는 구현 시 별도 버전으로 확정한다.

### 3.2 점수 설계

첫 후보 방식은 설명 가능한 **구간 기반 구조화 점수 + 공동 decoding**이다. 다음 식은 설계이며 구현 완료가 아니다.

```text
전체 점수 = 각 구간의 화음·음표·NCT 특징 점수 합
          + 인접 화음·조성·해결·경계의 전이 특징 점수 합
          + 길이·분할 복잡도 특징 점수
```

주요 특징군:

1. 구성음의 지속·재타격·누적 제시, 원음 철자와 음가, 구성음 생략 가정.
2. 경과/보조·계류·선행 등 후보 아래의 조건부 음표 설명. 서로 충돌하는 성부/NCT 가정의 유리한 값은 합치지 않는다.
3. 관측 최저음과 근음·전위 후보, 페달과 구성음 베이스의 대안.
4. 새 구별 구성음, 화음 외 음이 지속/해결되는 방식, 분산형이 완성되는 시간, 유지·교체의 경쟁 근거.
5. 이끎음/7음의 실제 해결과 지연·비전형 진행, 적용화음·목표 화음의 관계.
6. 조성 일관성과 변화, 박절에 상대적인 길이·분할 비용. 마디마다 화음을 강제하거나 화음 수가 많을수록 유리하게 하지 않는다.

동일 음표에서 유래한 membership·pitch pool·설명 음가 등 상관된 특징이 독립적인 여러 표처럼 중복 보상되지 않도록 정규화·정규화 계수와 ablation으로 점검한다. 미판정 특징은 availability/mask와 함께 저장하며0=불성립으로 치환하지 않는다. 유리수 시간은 IR과 경계에서 유지하고 ML용 수치 변환의 단위·정밀도만 명시한다.

참조 누락·음가 손상·음표 발명·겹치거나 빠진 출력 partition은 유효성 위반이다. 반면 “7음이 전형적으로 내려가지 않았다”, “모든 구성음이 관측되지 않았다”, “페달 해석을 아직 지원하지 않는다”는 자동 전체 탈락 조건이 아니다. **해결 템플릿 불일치와 음악적 불가능을 구별**하고 해당 점수·미지원·불확실성으로 표현한다. 원 근거 진단의 `false/null` 자체를 임의로 바꾸지는 않는다.

구간/인접 전이로 분해 가능한 첫 점수에는 semi-Markov DP를 사용한다. 이전 화음·조성처럼 미래 점수에 필요한 상태를 보존해야 하므로 기존 `(끝,구간 수)`만으로 충분하다고 가정하지 않는다. 비인접 해결·긴 성부/페달 의존은 상태 확장 또는 명시된 beam 근사로 다루고, 근사 탐색을 exact 최적해로 표시하지 않는다.

첫 선택기는 이미 materialize한24개 path만 재순위화하는 baseline과, lattice에서 직접 학습 점수로 decode하는 버전을 분리 비교한다. 전자는 빠른 출발점이지만 정답이24개 밖에 있으면 절대 회복할 수 없다. 필수 선택 계산을 모든 후보 쌍의 거대 JSON 저장 완료에 종속시키지 않는다. 후보별 특징 캐시·상위 대안·필요한 설명을 저장하고 과거 전수 비교 archive는 그대로 보존한다.

### 3.3 가중치 학습

- 첫 실험은 규칙 특징의 선형 segmental scorer로 시작하되, 이는 음악 이론을 단순화해 폐기하려는 것이 아니라 기존 근거가 실제 선택에 기여하는지 측정하기 위한 기준선이다.
- 첫 학습 후보는 structured perceptron이며, 경계·화음이 연결된 전체 진행의 오차로 업데이트한다. train/dev 결과에 따라 segmental CRF 등으로 확장한다. 우선 사용할 라이브러리와 학습 자격은 manifest 단계에서 확정한다.
- DCML train에서 가중치를 학습하고 dev에서 규제·길이 비용·탐색 폭을 선택한다. test를 본 뒤 같은 test의 가중치를 바꾸고 독립 정확도로 보고하지 않는다.
- DCML 화성 라벨만으로 모든 음표의 NCT 정답이나 전형적 해결 의무를 직접 학습했다고 주장하지 않는다. 해당 역할은 잠재 가정/특징 또는 별도 주석 과제다.
- gold 진행이 후보에 없으면 그대로 후보 누락으로 집계한다. gold를 이용한 training-only 보충 실험은 별도 arm이며, test 후보 생성에 gold 경계·key·label을 전달하지 않는다.
- 초기 점수와 점수 차이는 보정된 확률이 아니다. calibration과 coverage 실험 전에는 임의 `confidence=0.95`를 만들지 않는다.

## 4. 데이터의 충분성과 한계

DCML은 현재 첫 고전 기능화성 모델의 학습·평가를 시작할 합리적인 자료다. 다만 “이미 모든 목적에 충분하다”는 결론은 아직 없다. 실제 정렬·중복·어휘·작곡가·편성별 유효 분모와 성능으로 판단한다. 피아노 자료의 성능을 관현악·팝·작곡/편곡 역할 이해까지 일반화하지 않는다.

공식 [DCML 표준](https://dcmlab.github.io/standards/build/html/reference/reference.html)은 화성 시작에서 다음 라벨까지의 유효 범위, 분석 속도의 일관성, 계류·지연·추가음과 장식음 주석 범위의 차이를 명시한다. 경과음·보조음을 전부 음표별 gold로 주는 자료가 아니다. 데이터의 명시적 라벨과 프로그램이 유추한 음표 역할을 구별한다.

팝 Melody 화음 파트의 활용:

1. 파일명뿐 아니라 part/staff·음표·duration·tie·박절과 화음 파트를 확인한다. 전조 악기라면 concert pitch를 맞춘다.
2. 단순 수직 음집합, 실제 베이스, 화음이 펼쳐지는 시간창을 보존하고 root/quality/inversion 약한 후보를 추출한다.
3. 같은 작품의 Melody/Piano/실내악 판본을 비교하되 모두 동일 작품 가족에 묶는다. 다른 분할로 들어가면 시험 정보가 누출된다.
4. 화음 파트가 한 마디를 길게 대표하거나 일부 구성음이 생략된 경우를 명시한다. 임의로 실제 화성 경계를 같은 길이로 확정하지 않는다.
5. 처음에는 weak/silver supervision 또는 조건부 prior다. 사람 검수 또는 신뢰 가능한 별도 화성 주석 연결 없이 Roman/function/local key gold로 승격하지 않는다.

이 자료가 다른 팝 주석보다 반드시 더 중요하다는 주장은 현재 비교 실험이 없다. 편곡 원자료로서의 유용성과 분석 정답으로서의 자격은 각각 평가한다. 고전 DCML 학습과 팝 weak-data 준비는 분리하며 전자는 후자를 기다리지 않는다.

**2026-10-04 추가 검토 반영:** “처음에는 weak/silver”는 **화성 분석 과제**에 대한 자격이다. 해당 편곡을 재현하는 조건부 편곡 학습에서는 실제 화음 파트의 pitch/onset/duration/tie 등이 **기보 target 정답**이다. 편곡의 유일한 정답이나 Roman/function 정답이라는 뜻은 아니다. 원자료/정렬/사용 권한과 작품 가족 분할은 두 과제 모두 확인하며, target이 있다는 이유로 기존 학습 제한을 자동 해제하지 않는다.

## 5. 공개 모델과 공통 평가

[ChordGNN 공식 논문](https://arxiv.org/html/2307.03544v2)의 §4–5와 Table1은 key·degree·quality·inversion·root·RN을 구분하고, 대부분은 시간 가중 CSR, RN(Onset)은 onset 정확도로 보고한다. 동일 분할을 쓰는 것이 비교 조건이다. 같은 표에서 root 성능과 전체 Roman 성능은 서로 다르므로 우리도 “정확도” 한 숫자로 합치지 않는다.

[ChordGNN 공식 코드](https://github.com/manoskary/chordgnn)는 음표 특징에서 onset별 예측을 만드는 비교 대상이다. 현재 archived repository이므로 버전·의존성·실행 재현 가능성을 먼저 확인한다. [AnalysisGNN 공식 코드](https://github.com/manoskary/analysisgnn)는 음표 단위 다중 과제를 제시하지만 README에 개발 중임을 명시하며 RN resolve 및 onset/beat 집계가 TODO다. 실행·출력 adapter 검증 전에는 동등한 완제품으로 취급하지 않는다.

두 비교 트랙:

- **로컬 공통 benchmark:** 모든 모델에 같은 score/무주석 입력, 같은 blind test, 공통 라벨 매핑과 evaluator를 사용. 모델의 학습 자료 중복이 없다고 확인된 경우에만 독립 비교라고 표시한다.
- **논문 재현 benchmark:** 가능한 경우 공개된 split·dataset revision·라벨/시간 grid·모델 checkpoint를 그대로 재현. 로컬 재분할 성능을 논문 표에 직접 삽입하지 않는다.

사전학습 모델의 train이 DCML/When-in-Rome 등과 겹치거나 알려져 있지 않다면 overlap-known/unknown으로 표시한다. 우리가 그 작품을 새 holdout으로 지정했다는 이유만으로 외부 모델의 학습 이력이 없어지지 않는다. 공통 축소 어휘 비교와 우리 전체 어휘 진단을 별도로 둔다.

첫 평가표의 필수 열:

| 지표 | 계산·보고 원칙 |
|---|---|
| 후보 ceiling | 라벨별 oracle coverage, gold 경계/전체 진행의 표현 가능성과 보존 path 안의 최선 성능. Gold 사용은 evaluator 내부에서만 |
| Root/quality/inversion/key/degree/RN | 정확한 공통 라벨 정의. 시간 가중 일치율과 작품별 macro 평균을 구별 |
| 논문 호환 CSR | 해당 논문과 같은32분음표 grid 및 라벨 정의로 별도 계산. exact rational 시간 적분 결과와 혼동하지 않음 |
| 화성 경계 precision/recall/F1 | 출력 공통 어휘에서 의미 있는 라벨 변화 기준. Exact 및 미리 정한 박자 상대 tolerance를 별도 보고, 한 경계에 여러 정답을 중복 매칭하지 않음 |
| 과병합/과분할 | 경계 누락·추가와 영향을 받은 음표/음가·구간을 저장 |
| Coverage/abstention | 전체 적격 시간·작품 분모, 실제 선택 비율, 미지원/실패. 보류한 어려운 구간을 지운 정확도로 표시하지 않음 |
| 일반화·유형별 오류 | 작곡가·작품 가족·편성 및 secondary/전위/분산형 등. 별도 정답이 없는 NCT/질감 태그는 proxy라고 명시 |
| 실제 비용 | 전곡 추론 시간·peak memory·실패율·모델/규칙/입력 revision. 후보·pair 수는 정확도 열이 아님 |

Gold의 조성/기능을 입력으로 제공한 oracle-key 실험은 상계 진단이며 blind RN 성능과 분리한다. 표현 변환 불가능·미지원 라벨·주석 공백의 규모도 전부 보고한다. 원주석의 의심 오류는 원본을 고치지 않고 별도 reviewer correction으로 보존한다.

## 6. 다음 개발의 순서와 완료 기준

| 순서 | 해야 할 큰 기능 | 완료 산출물 |

J0과J1을 최소 필요한 범위에서 이어서 수행하고 **전체17개 코퍼스의 완벽한 정렬, 모든 교재 예외 또는 모든 지연 해결 규칙 완료를 첫 선택·평가의 전제조건으로 삼지 않는다.** 이미 적격인 학습/개발 작품으로 시작하되 평가 분모와 미지원 범위를 숨기지 않는다. 첫 기준선은 성능이 낮아도 재현 가능한 실패를 드러내는 것이 목적이다.

**J0 파일럿 timebox:** 첫 자료 정리는 active 작업 최대30분 후 범위를 동결한다. 그 안에 쓸 수 있는 기존 manifest/정렬 자료로 J1을 시작하고 미지원/미검증 항목은 이유·분모와 함께 보존한다. 새 인프라·모든 판본 재정렬을 추가하지 않는다. 기존 노출된 train/dev의 첫 숫자는 독립 test라고 부르지 않는다. 학습/새 test 자격 확정은 별도 잔여 항목이다.

**실행 후속:** [첫 recall@24·선택 기준선](2026-10-04-candidate-recall-and-first-selection.md)에서 기존322문맥을 실제 처리했다. 후보 정답 포함65/256, 단순 선택5/256이며 root+spelled members/time의 개발 진단이다. 이 원 검토 기록의 §7 미실행 목록은 작성 당시 이력으로 보존하고, 현재 구현/수치는 후속 기록을 따른다. 다음은24path 밖/원 lattice 밖 오류를 구별한 뒤 학습 점수로 연결한다.

이미 사용자와 규칙을 조정한 베토벤 소나타1번·8번 등의 사례는 개발/회귀 자료다. 이 사례의 재검사 성공을 새로운 blind test로 세지 않는다. 새 test를 보고 반복 개선할 때는 dev로 전환한 이력 또는 별도 최종 holdout을 관리한다. 코퍼스 이름만으로 DCML/When-in-Rome/ChoCo 간 중복을 없앴다고 주장하지 않는다.
